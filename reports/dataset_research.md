## Dataset 1: OSIRIS

### Purpose and Origin
**Full name:** OSIRIS — *Open Scalable layout generatIon and paRasitic-aware annotatIon pipeline for analog System/circuit design*

**Paper:** "OSIRIS: Bridging Analog Circuit Design and Machine Learning with Scalable Dataset Generation" — accepted at **ICLR 2026**

**Authors:** Giuseppe Chiari, Michele Piccoli, Davide Zoni (Politecnico di Milano)

**Problem addressed:** The critical bottleneck of scarce open, high-quality, large-scale datasets for ML in Analog/Mixed-Signal Electronic Design Automation (AMS-EDA). Unlike digital IC design, analog layout has historically been a manual, iterative process with no open benchmarks.

**Key capability:** Systematically explores the analog design space by enumerating transistor finger arrangements and component position perturbations, producing DRC-clean, LVS-verified layout variants with parasitic-aware performance annotations.

---

### Known Columns / Features

> **Note:** OSIRIS is NOT a simple flat CSV dataset. It is a structured archive containing layout geometry files (GDSII), netlists, metadata files, and performance result files. The schema below reflects confirmed fields from paper descriptions and Hugging Face repository metadata.

#### Layout / Design-Space Features (Inputs — PRE-simulation)
| Feature Group | Fields | Type | Description |
|---|---|---|---|
| Circuit topology | `topology` / `circuit_id` | string | Analog block type (e.g., Miller-compensated 2-stage op-amp, folded cascode) |
| Transistor fingers | `finger_count`, `finger_arrangement` | int / categorical | Number and configuration of parallel gate fingers per transistor |
| Component placement | `x_pos`, `y_pos`, `orientation` | float / enum | Spatial coordinates and rotation of each device in the layout |
| Position perturbations | `perturbation_id`, `delta_x`, `delta_y` | float | Systematic offset applied to component positions |
| Device sizing | `W` (width), `L` (length), `multiplicity` | float | Transistor geometry parameters from netlist |
| Netlist reference | `netlist_id`, `template_id` | string | Reference to schematic template from which layout was derived |
| DRC status | `drc_clean` | bool | Whether the variant passes Design Rule Checking |
| LVS status | `lvs_verified` | bool | Whether the variant passes Layout Versus Schematic check |

#### Parasitic Elements (POST-layout extraction)
| Field | Type | Description |
|---|---|---|
| `parasitic_capacitance` | float (F) | Extracted interconnect capacitances from routing |
| `parasitic_resistance` | float (Ω) | Extracted interconnect resistances from routing |
| `rc_network_id` | string | Reference to full RC parasitics extracted netlist |

#### Performance Metrics / QoS (POST-layout simulation targets)
| Metric | Type | Unit | Description |
|---|---|---|---|
| `dc_gain` | float | dB | Low-frequency small-signal differential voltage gain |
| `gain_bandwidth_product` (GBW) | float | Hz | Unity-gain bandwidth |
| `phase_margin` | float | degrees | Stability margin of the feedback loop |
| `slew_rate` | float | V/μs | Max rate of output voltage change under step input |
| `cmrr` | float | dB | Common-Mode Rejection Ratio |
| `power_consumption` | float | W | Total quiescent power dissipation |
| `area` | float | μm² | Physical footprint / bounding box of the layout |
| `settling_time` | float | s | Time for output to settle within spec after step input |

---

### Target Variables (What Can Be Predicted)

The dataset enables multiple prediction tasks:

1. **Post-layout performance regression** — predict any/all QoS metrics (gain, GBW, phase margin, slew rate, CMRR, power, area) from pre-layout inputs (device sizing + placement + finger arrangement)
2. **Parasitic prediction** — predict extracted RC parasitics from layout geometry, without running full PEX
3. **Layout quality scoring** — predict DRC pass/fail or layout feasibility from early-stage placement
4. **Performance degradation** — predict delta between pre-layout (ideal) and post-layout (parasitic-degraded) metrics
5. **Optimal placement search** — RL reward modeling for placement optimization

### PRE-layout vs POST-verification Features

| Phase | Available Features | Notes |
|---|---|---|
| **PRE-layout** | Netlist topology, transistor W/L, finger counts, multiplicity, schematic performance specs | Available from SPICE netlist before any physical layout |
| **PRE-verification** (layout done, not simulated) | Component positions (x, y, orientation), finger arrangements, perturbation IDs, DRC status | Available after layout generation, before PEX simulation |
| **POST-verification** (PEX + simulation complete) | All QoS metrics (gain, GBW, PM, SR, CMRR, power, area), parasitic R/C values | **TARGETS only** — using these as inputs to predict further downstream targets constitutes leakage |

### Known Limitations

- **Narrow circuit scope:** Primarily covers Miller-compensated two-stage op-amps and closely related topologies. Generalization to arbitrary analog blocks is unconfirmed.
- **Technology node undisclosed:** The specific CMOS process node used is not fully disclosed in public sources.
- **No standard train/test split:** Data is delivered as a monolithic ZIP; users must implement their own splitting strategy.
- **Non-tabular primary format:** Raw data is GDSII + SPICE, not flat CSV/Parquet. Requires preprocessing before ML ingestion.
- **Large download:** ~4.27 GB total; impractical for quick experiments without sampling.
- **Post-layout targets only:** No pre-layout ideal simulation values are confirmed to be included for direct comparison (degradation modeling would require separate pre-layout simulation).
- **RL baseline dependency:** The RL baseline code requires the full OSIRIS simulation environment (not just the static dataset), limiting offline use cases.
